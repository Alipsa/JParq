# Plan for the v1.4.0 issues

Source: [v1.4.0-issues.md](v1.4.0-issues.md). Sections 2–4 retain the baseline and implementation approach
at `4b7a0e3`; issues 1–3 were implemented and verified in `91ab8e2`, as recorded below. Later review probes
reconfirmed the issue 2 derived-table fixes and the open issues 4–5, and identified the pre-existing CTE
row-bounds bug recorded as issue 6. The CTE bug reproduces on both `4b7a0e3` and `91ab8e2`.
Sections 6–9 record the follow-up implementation and acceptance criteria for issues 4–6.

## Implementation notes

- Issue 1 adds Parquet-backed tests without changing the existing window-prefetch fix. Processor-owned
  hardening for the public buffering options was subsequently added after the issue 6 reachability audit.
- Issue 2's failure was reproduced in the new tests. The outer plan inherited inner sorting and row bounds
  even though the derived table had already executed them during materialization. Re-evaluating an inner
  correlation against projected outer rows caused the missing-column error. The parser now leaves those
  operations in the inner scope for derived tables in `91ab8e2`; the old compensating subtraction of inner
  offsets was also removed. The follow-up issue 6 fix extends this boundary to materialized CTEs.
  Alias-shadowing coverage also exposed outer substitution of query-local aliases. The correlation rewriter
  now tracks local SELECT bindings and excludes them from both expression rewriting and text fallback.
- Issue 3's type and string-materialization failures were reproduced. Shared Boolean-expression recognition
  now drives computed metadata and value evaluation. Both `columnSchema` and `mapSqlTypeToAvroType` already
  map `Types.BOOLEAN` correctly and remain unchanged; tests exercise both mappings with accurate metadata.
  Result sets retain schema metadata independently of the current row, and set-operation metadata reports
  Java class names. Bare-column predicates worked once types were preserved; `IS [NOT] UNKNOWN` required
  explicit evaluator support, including for projections and HAVING.
- Tests are in `src/test/java/jparq/derived/Version140RegressionTest.java` and
  `src/test/java/jparq/meta/JParqResultSetMetaDataTest.java`, with direct scope tests in
  `src/test/java/jparq/engine/CorrelatedScopeTest.java`. They cover all four independent pushdown settings
  for the main reproductions, exact window values/cardinality, query-scope controls, and Boolean type stability.
- Issue 6: the new tests first reproduced double OFFSET application (`[3, 4]` instead of `[2, 3, 4]`).
  `parsePlainSelect` now plans only the consuming SELECT's relational operations. The wildcard audit also
  reproduced lost CTE aliases and recomputed row numbers; wildcards now read the materialized input schema.
  Empty wildcard results retain their schema metadata, and the prefetched row cannot leak through `LIMIT 0`.
  Tests extend `Version140RegressionTest.cteBoundsBelongToTheirOwnScope` and
  `cteWildcardsPreserveMaterializedValues`, reusing the existing four-row, empty, and single-row fixtures.
- Issue 4: the new tests first reproduced `Unknown column for DISTINCT: rn`. DISTINCT keys now evaluate
  the positional SELECT expressions with the shared value evaluator after windows are computed, retaining
  record identity and the original window state. Positional keys also preserve duplicate projection labels.
  No additional window cache is needed: the window values remain in `WindowState` through output evaluation.
  Non-window DISTINCT retains streaming execution. `WindowPlan.inputExpressions()` consolidates both
  consumers' dependency collection and includes previously omitted navigation-window ordering/default inputs.
  Existing numeric key equality is unchanged. A mixed INTEGER/BIGINT navigation default can still produce
  separate keys for numerically equal Java values; see the separate numeric limitation in the issue document.
  Tests extend `Version140RegressionTest.distinctUsesEvaluatedWindowProjections`; `id > 2` supplies the two
  equal-sized partitions instead of adding a separate `grp` field to the existing fixture.
- Issue 5: the new tests first reproduced `[FALSE, TRUE, NULL]` for `ASC NULLS FIRST`. `SetOrder` and
  `ResolvedSetOrder` now retain the NULL directive; comparison uses `OrderingUtil.compareNulls` independently
  of non-NULL direction. The original four-argument public `SetOrder` constructor remains available.
  `Version140RegressionTest.setOrderingPreservesNullDirectives` covers Boolean/numeric keys, expressions,
  ordinals, multiple keys, defaults, all set operators, duplicate NULLs, and final row bounds.
- Original verification on Java 21: the baseline `mvn verify` passed. `mvn spotless:apply verify` passed
  1,010 unit tests and three integration tests with no failures, errors, or skips, all coverage requirements
  met, and no Checkstyle, PMD, or Spotless violations. Earlier failures were also checked with the required
  skip-flags diagnostic command; completion uses the final unskipped build.
- Review follow-up after `957cd04`: metadata tests reproduced INTEGER expressions incorrectly reported as
  BOOLEAN when another join projection had the same source-column label. Metadata now retains the reader's
  source mappings separately from projection/correlation aliases. Boolean inference and navigation-function
  type lookup resolve qualified source fields without result-label fallback; unresolved or ambiguous
  references cannot establish Boolean output. The original metadata constructor remains supported for
  schema-only callers, resolving qualified references through canonical `qualifier__column` field names.
  The empty-join reproducers also failed before this follow-up. `executeQuery` now supplies the join reader's
  combined schema for metadata even when pushdown removes every physical row. Wildcard output comes from
  that schema before hidden predicate dependencies are added, keeping output shape consistent as well as types.
  Regression coverage extends `computedBooleanMetadataIsStatic`, with Parquet-backed
  `joinComputedMetadataKeepsSourceTypes` and `emptyJoinMetadataDoesNotDependOnPushdown` under all four settings.
  `JParqResultSet` no longer forwards obsolete pre-stage flags from parsed SELECTs; the public processor
  options and their direct compatibility tests remain intact. The tracker and plan stay in `todo/` while
  their separately documented derived-set-operation and numeric DISTINCT limitations remain open.

## 3. Issue 2: resolve correlated table-name qualifiers in derived-table ordering

### Baseline at `4b7a0e3` and implementation approach

1. Use the queries and four-row fixture below to reproduce the trigger: the correlation qualifier equals
   the base table name, whether the table is unaliased (`FROM o`) or explicitly aliased to the same name
   (`FROM o o`). Use `FROM o t` with correlation through `t.label` as the passing control on the same fixture.
   The expected limited ID set is `{1, 3, 4}`; assert sequence only where the SQL guarantees ordering.
2. Trace derived-table planning in `SqlParser`, including flattening, alias rewriting, and `preOrderBy`,
   then dependency collection, validation, and projection in `JParqPreparedStatement`.
3. Inspect `requiredColumns`, `collectColumnsForTable`, `ColumnsUsed`, and `SqlParser.collectQualifiedColumns`.
   Establish whether the failure is a lost outer dependency, a qualifier rewrite, an inner-local column
   incorrectly required from the outer table, a correlation context restricted to projected labels, or qualifier
   normalization when the qualifier matches the base table name.
   Inspect `JParqResultSet`'s `correlationLabels`, `proj`, and qualifier mapping construction around lines 519–530.
   The available-columns diagnostic supports investigating projected-label context. The `U:o` diagnostic
   also warrants tracing qualifier normalization, but neither establishes the root cause or the meaning of
   `U:` in this failure without inspecting its construction.
4. Fix the layer identified in step 3, whether dependency collection, qualifier normalization, or correlation
   context construction. Retain correlated outer columns through sorting and correlation mapping while
   keeping inner-local columns in their own scope, for both ordinary and pre-stage ordering.
5. Treat projection pushdown as secondary: the failure occurs with it enabled and disabled, so investigate
   correlation context and scope before column pruning. Keep validation active in both modes. Retain existing
   missing-column and ambiguous-column errors; keep hidden dependencies out of output columns.
6. Confirm inner sorting and limiting finish before outer filtering, ordering, or limiting.

### Primary reproducer and baseline

Create table `o` with these rows:

| id | label |
| --- | --- |
| 1 | d |
| 2 | a |
| 3 | c |
| 4 | b |

The correlated counts are `d → 3`, `a → 0`, `c → 2`, and `b → 1`. Descending count and `LIMIT 3` select
IDs `{1, 3, 4}`. An outer query without `ORDER BY` guarantees only that set, not its iteration order.

```sql
SELECT id FROM (
  SELECT id FROM o
  ORDER BY (SELECT COUNT(*) FROM o i WHERE i.label < o.label) DESC, id
  LIMIT 3
) x
```

On `4b7a0e3`, this fails for both projection pushdown settings with
`Unknown column 'label' for qualifier 'U:o'`. Available columns contain only `id` and the sort expression.
The original missing-column diagnostic is historical and must not be the required failure signature.
An explicit alias equal to the base table name also fails:

```sql
SELECT id FROM (
  SELECT o.id FROM o o
  ORDER BY (SELECT COUNT(*) FROM o i WHERE i.label < o.label) DESC, o.id
  LIMIT 3
) x
```

The passing control changes only the alias and its references:

```sql
SELECT id FROM (
  SELECT t.id FROM o t
  ORDER BY (SELECT COUNT(*) FROM o i WHERE i.label < t.label) DESC, t.id
  LIMIT 3
) x
```

Thus the trigger is qualifier equality with the base table name, not alias absence. Commit `0e6de97` may
explain success when the alias differs from the table name; that attribution remains unverified.

### Regression coverage and acceptance

- Fix both `FROM o` and `FROM o o` reproducers. Also fix the unaliased variants without inner `LIMIT` and
  with outer `ORDER BY id`; these already fail. Assert expected IDs/cardinality and absence of correlation errors.
- Preserve the already-passing `FROM o t` control, equivalent CTE, ordinary non-derived query, projection including
  `label`, and equivalent correlation in the inner `WHERE`. These are regression-only controls.
- Exercise correlation columns omitted from the projection, table aliases, renamed projections, quoted
  identifiers, and alias shadowing inside the scalar subquery.
- Include inner-local columns absent from the outer schema, nullable correlation values, and an outer
  `ORDER BY`/`LIMIT` that differs from the inner ordering and limit.
- Run the reproducer with projection and predicate pushdown independently enabled and disabled.
- Assert output column count/labels and that genuinely invalid references still fail.

Relevant suites: `OptimizedPredicateTest.orderByProjectionIncludesAllRequiredInputs`, `OrderByTest`,
`SqlParserDerivedTableLimitTest`, and `DerivedAndCteCorrelationTest`.

## 4. Issue 3: retain Boolean types through projections, derived tables, and CTEs

### Baseline at `4b7a0e3` and implementation approach

`JParqResultSetMetaData.resolveComputedColumnType` recognizes analytic expressions and arrays but falls back
to `Types.OTHER` for Boolean predicates. `JParqPreparedStatement.buildSubquerySchema` consumes this metadata;
`columnSchema` maps `OTHER` to Avro `STRING` through its default branch, while `inferSubqueryColumnSchema`
only handles plain `Column` projections. `mapSqlTypeToAvroType`, used for set-operation ordering, has the
same fallback and must be considered alongside `columnSchema`.

Review probes report direct Boolean values with `OTHER` metadata, but derived-table and CTE values become
strings with `VARCHAR` metadata. Empty derived results instead report `OTHER`, demonstrating data-dependent
metadata. Derived `WHERE c` and `WHERE c IS TRUE` fail with `Unsupported predicate: c`; physical Boolean
passthrough already works. These are baseline observations to capture in tests.

1. Add metadata tests for direct computed Boolean projections and integration tests for derived/CTE forms.
2. Infer Boolean output from expression structure and declared types, independently of observed row values.
   Cover Boolean literals, comparisons, logical operators, predicate expressions, and explicit Boolean casts.
   Use `CAST((n > 1) AS BOOLEAN)`: the unparenthesized `CAST(n > 1 AS BOOLEAN)` fails in JSqlParser before
   execution and is not an acceptance case for this fix.
   Unwrap parentheses and handle Boolean-valued `CASE`/`COALESCE` consistently where their types are known.
3. Reuse existing type-inference helpers where appropriate and keep JDBC type/class reporting and materialized
   Avro schemas consistent. Check both `columnSchema` and `mapSqlTypeToAvroType` so their handling does not
   drift. Avoid creating separate Boolean-expression lists that can drift across layers.
4. Preserve nullable Boolean values during materialization and coercion. SQL UNKNOWN must remain `null`;
   do not stringify values or infer the type only from the first non-null row.
5. Keep predicates on derived Boolean columns compatible with the existing SQL three-valued evaluator.
   After the schema reports `BOOLEAN`, verify bare-column and `IS TRUE` predicates explicitly. If
   `Unsupported predicate: c` persists, trace where the evaluator rejects a bare Boolean column on a derived
   schema and fix that path within this issue. Do not reopen unrelated predicate-semantics work.

### Regression coverage and acceptance

- For `n > 1 AS c`, direct, derived-table, nested-derived, and CTE results return `Boolean.FALSE`,
  `Boolean.TRUE`, or `null` from `getObject`, according to fixture values.
- Metadata reports `Types.BOOLEAN`, type name `BOOLEAN`, and class name `java.lang.Boolean`, including
  before iteration, a first-row NULL, all-NULL results, and an empty result for a statically Boolean expression.
- `getBoolean` returns the expected primitive value; `wasNull` distinguishes SQL NULL from FALSE.
- `WHERE c`, `WHERE NOT c`, `c IS TRUE`, `c IS FALSE`, and `c IS UNKNOWN` select the correct rows.
- Cover computed comparisons, `AND`/`OR`/`NOT`, `IS NULL`, `BETWEEN`, `IN`, `LIKE`, `EXISTS`, literals,
  casts, and Boolean-valued `CASE`/`COALESCE`, including UNKNOWN where applicable.
- Physical Boolean passthrough such as `ab AS c` remains correct. Strings containing `"true"` or `"false"`
  remain strings unless explicitly cast.
- Add top-level `UNION` and `UNION ALL` cases, including
  `SELECT n > 1 AS c FROM o UNION ALL SELECT n > 3 FROM o`, which currently reports `OTHER`.
  Assert Boolean metadata, values, NULL preservation, and appropriate duplicate handling; cover set-operation
  ordering to exercise `mapSqlTypeToAvroType`.
- Check consistency with projection and predicate pushdown enabled and disabled; assert expected values
  independently of agreement between the two execution modes.

Extend `src/test/java/jparq/meta/JParqResultSetMetaDataTest.java` for computed-column metadata coverage.
This is distinct from `src/test/java/jparq/JParqResultSetMetaDataTest.java`, which tests basic metadata.
Also extend suites in `jparq.derived` and existing Boolean/NULL tests for execution behavior.

Wrapping a set operation in a derived table currently throws `ClassCastException` (`SetOperationList` cast to
`PlainSelect`). Track that separately in [derived-set-operation.md](derived-set-operation.md); fixing that
pre-existing parser/planner defect is outside this plan. Top-level set-operation Boolean typing remains in scope.

## 7. Issue 4: support DISTINCT with computed window projections

Status: implemented; final verification is recorded in section 9. Source: issue 4 in [v1.4.0-issues.md](v1.4.0-issues.md).
The earlier verification above applies to issues 1–3; section 9 records the combined follow-up verification.

### Baseline at `91ab8e2`: reproduce and identify the execution boundary

1. Add failing Parquet-backed cases in `Version140RegressionTest.distinctUsesEvaluatedWindowProjections`,
   reusing the existing fixture with IDs 1–4 and `n = [1, NULL, 3, 4]`, plus empty/single-row variants.
   Partition by `id > 2` to produce two partitions of two rows.
2. Reproduce `SELECT DISTINCT id, ROW_NUMBER() OVER (ORDER BY id) AS rn FROM o`. Assert exactly
   `(1, 1), (2, 2), (3, 3), (4, 4)` when ordered by `id`, including aliased and unaliased projections.
3. Trace `JParqResultSet.resolveDistinctColumns`, `QueryProcessor.distinctKey`, `applyDistinct`,
   `bufferAndSort`, and `ValueExpressionEvaluator`. The current key builder expects physical fields, and
   buffered DISTINCT runs before `WindowFunctions.compute`. Confirm both problems in tests before choosing
   where to implement projection-aware DISTINCT.

### Implementation

1. Compute windows over all qualifying input rows before applying DISTINCT for the current SELECT. Then
   deduplicate the complete projected tuple, including computed and physical expressions, before final
   ordering, offset, and limit. Do not remove input duplicates before window computation.
2. Build DISTINCT keys from evaluated projection expressions using the same correlation mappings, aliases,
   and `WindowState` as ordinary projection evaluation. Reuse evaluation and value-comparison helpers;
   avoid resolving computed expressions as physical field names or parsing their display labels as SQL.
3. Preserve record identity while using `WindowState`, whose results are keyed by record identity. Keep
   computed values available through deduplication, sorting, and output without recomputing windows on the
   reduced row set. Decide whether values need caching after tracing the existing evaluation lifecycle.
4. Preserve streaming DISTINCT for simple physical projections. Inner-query DISTINCT executes during
   materialization, before the consuming SELECT. The issue 6 audit removed the remaining SQL producer of
   pre-stage options; public staged options remain for compatibility, with separate prefetch hardening tested
   in `QueryProcessorPrefetchTest` (see section 2).
5. Preserve existing SQL NULL equality for duplicate elimination and established value comparisons. Avoid
   expanding this fix into unrelated numeric DISTINCT or GROUP BY behavior changes.

### Regression coverage and acceptance

- Direct DISTINCT with `ROW_NUMBER` returns four rows and correct window values; `LIMIT 2` returns the first
  two unique projected rows, with outer ordering explicit for deterministic assertions.
- `SELECT DISTINCT COUNT(*) OVER () AS total FROM o` returns one value, `4`. Partitioned COUNT returns one
  value, `2`, for the fixture above. These cases prove that windows see all rows before duplicate removal.
- Cover ranking, aggregate, and navigation functions; mixed physical/computed projection tuples; aliases;
  NULL window results; and a Boolean expression containing a window function. Compare complete output tuples.
- Cover projected duplicates with different unselected source columns, plus ordinary scalar expressions,
  to verify that keys reflect the SELECT list rather than the entire source record.
- Cover WHERE filtering, empty/single-row input, `LIMIT 0`, LIMIT/OFFSET after DISTINCT, and ordering by
  projected aliases or ordinals. Assert metadata and exhaustion as well as values and counts.
- Preserve the existing outer-DISTINCT derived-table case and physical-column DISTINCT behavior. Run the
  primary cases under all four independent predicate/projection pushdown settings, using fixed expectations.

Relevant existing coverage: `src/test/java/jparq/derived/Version140RegressionTest.java`, `src/test/java/jparq/window`,

## 8. Issue 5: honor explicit NULL ordering in set operations
