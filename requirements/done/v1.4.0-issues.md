## Jparq issue 1 (window functions)

A window function returns one extra copy of the first row: a 4-row table gives (1,1) (1,1) (2,2) (3,3) (4,4) for SELECT id, ROW_NUMBER() OVER (ORDER BY id) FROM t, while COUNT(*) is 4. main does the same and I haven't found the cause; it needs its own issue.

I've confirmed the duplicate shows up across every window function I tested, which points to an issue in how the first prefetched row is handled. Now I'll check whether non-window-function queries using the same buffered path are also affected.

It happens with every window function, and it doesn't depend on the data. The duplicate appears when three conditions hold together:
- the SELECT list contains a window function,
- the outer query has no ORDER BY and no OFFSET,
- the first row read from the file passes the WHERE filter, or there is no filter.

main behaves the same way, so this bug predates PR #186.

Derived tables with an inner LIMIT, ORDER BY … LIMIT or OFFSET (and no window function) returned the right rows.

Likely cause (from the code; I haven't tested a fix)

JParqResultSet reads the first record in advance. When the query has no ORDER BY (around line 541), it hands that row out directly:
boolean usePrefetchedAsCurrent = match && select.offset() == 0;
...
int initialEmitted = usePrefetchedAsCurrent ? 1 : 0;
...firstAlreadyRead(first)...windowPlan(windowPlan)
this.current = usePrefetchedAsCurrent ? first : qp.nextMatching();
When a window function is present, the QueryProcessor constructor (line 397) buffers every row and does add firstAlreadyRead to that buffer. That's needed so the window values are computed over all rows. The result set has already returned that same row as current, so it comes out twice. initialEmitted = 1 also counts that row against LIMIT, which explains the LIMIT 2 result.

A fix would be to stop handing out the prefetched row whenever the processor buffers:
boolean usePrefetchedAsCurrent = match && select.offset() == 0 && windowPlan.isEmpty();
The processor's pre-stage options (preLimit/preOrderBy/preOffset) take the same buffering branch, so they probably need the same guard. I haven't found a query that uses them on this code path, so that part is unverified.

A regression test would be SELECT id, ROW_NUMBER() OVER (ORDER BY id) FROM <4-row parquet>, expecting exactly 4 rows, plus a LIMIT 2 variant. ## Jparq Issue 3 (computed Booleans stored as strings)
Derived tables and CTEs store computed Booleans as strings. SELECT c FROM (SELECT n > 1 AS c FROM b) d returns the String "false". So WHERE c on a derived Boolean is rejected, while a physical Boolean column passed through (ab AS c) works. JDBC metadata reports OTHER for Boolean projections.

## Jparq Issue 4 (DISTINCT with a computed window expression)

For a four-row Parquet table `o` containing IDs 1–4:

```sql
SELECT DISTINCT id, ROW_NUMBER() OVER () FROM o
```

This throws `Unknown column for DISTINCT: ROW_NUMBER() OVER ()` because the DISTINCT key builder expects
physical schema fields. It explicitly rejects computed expressions rather than evaluating their result values.
Investigate evaluating DISTINCT after window projections, while retaining SQL ordering and limiting semantics.

The window cardinality regression suite instead covers the supported outer-DISTINCT form:

```sql
SELECT DISTINCT id FROM (SELECT id, ROW_NUMBER() OVER () AS w FROM o) x
```

## Jparq Issue 5 (explicit NULL ordering in set operations)

For nullable numeric values `n = [1, NULL, 3, 4]`:

```sql
SELECT n > 1 AS c FROM o
UNION
SELECT n > 3 FROM o
ORDER BY c NULLS FIRST
```

The observed result is `[FALSE, TRUE, NULL]`; the expected order is `[NULL, FALSE, TRUE]`.
`JParqPreparedStatement.compareSetRows` uses a fixed NULL comparison and does not honor explicit NULL ordering.
Investigate preserving NULL-order directives through set-operation parsing and comparison. Boolean typing and
set-order expression coverage use ordinary ordering independently of this limitation.


## Jparq Issue 6 (CTE ordering and row bounds reapplied after materialization)

Review probes reproduce this on both `4b7a0e3` and `91ab8e2`; it is pre-existing, not a regression introduced
by the issue 2 fix. For a Parquet table `o` containing IDs 1–4 in physical order:

```sql
WITH x AS (SELECT id FROM o ORDER BY id OFFSET 1 ROWS)
SELECT id FROM x;

WITH x AS (SELECT id FROM o ORDER BY id OFFSET 1 ROWS)
SELECT id FROM x ORDER BY id;

WITH x AS (SELECT id FROM o ORDER BY id LIMIT 2 OFFSET 1 ROWS)
SELECT id FROM x ORDER BY id DESC;
```

The first two queries return `[3, 4]` rather than IDs `{2, 3, 4}` (exact sequence `[2, 3, 4]` when the outer
ORDER BY is present). The third returns `[3]` rather than `[3, 2]`. Equivalent derived-table queries return
the correct rows. The aggregate control remains correct:

```sql
WITH x AS (SELECT id FROM o OFFSET 2 ROWS)
SELECT COUNT(*) FROM x;
```

It returns `2`, as expected.

`SqlParser.parsePlainSelect` excludes an inner select from order/bounds inheritance only when `subquerySql`
is non-null. CTE references set `innerSelect` but leave `subquerySql` null, so their operations are inherited
by the outer plan despite already being applied during CTE materialization. The issue 2 fix covers derived
tables only. See section 6 of [v1.4.0-issues-plan.md](v1.4.0-issues-plan.md) for the implementation plan.
